# FUTABUS API documentation

Staff ticket list: `GET /api/v1/staff/tickets` requires `ticket.view`, an active verified staff/operator account and company scope across trips, routes and buses. Returns real issued tickets newest first with 15-row pagination (`data`, `meta`), no-store headers, and optional exact ticket/booking code, phone, passenger name, departure date and ticket-status filters. The Staff processing page loads this list on entry and displays details from the authorized row data. This read-only endpoint does not create or alter bookings/payments.

Ticket usability is checked against server time on each list/detail request. An active ticket is usable only strictly before departure; at departure or later it has `display_status: expired`, `usable: false`, and a departure-passed label. The stored `status` remains unchanged; used/cancelled/refunded labels take priority. Filter `active` excludes departed tickets; `expired` selects active tickets at/past departure. Staff detail refreshes the row from the API when opened. This display check does not implement a boarding/check-in endpoint.

- Swagger UI: `/api/docs`
- OpenAPI 3.1 JSON: `/api/openapi.json`
- The UI is read-only. It disables "Try it out" because the SePay endpoint handles real payment events.
- The UI uses pinned Swagger UI assets from unpkg; the JSON specification remains available when that CDN is unavailable.

The specification covers the HTTP API routes currently registered: public content, trip search and seat availability, ticket lookup, token issuance, current account and booking history, Bearer-token payment intents, bus and vehicle-type management, health, and the SePay webhook. The web checkout remains available for guest bookings. Other admin resources and session-based OTP flows still require separate API contracts, authorization, and tests.

API clients can request a 30-day Sanctum Bearer token from `POST /api/v1/tokens` and revoke it at `DELETE /api/v1/tokens/current`. Apply the `2026_10_10_000003_create_personal_access_tokens_table.php` migration before using token endpoints. Account and booking-history APIs require an active, verified account and a Bearer token with the `api` ability. Never put tokens in examples or logs.

When adding an API route, update `openapi.json` in the owning feature change and extend the API documentation feature test to compare the documented method/path with `route:list`. Never put a real webhook key or customer data in examples.

Staff counter sales are owned by `Staff/TicketProcessing`. `GET /api/v1/staff/ticket-context` provides current identity and capabilities. `GET /api/v1/staff/ticket-trips`, `POST /api/v1/staff/ticket-sales` and `GET /api/v1/staff/ticket-sales/{sale}` require `booking.create` and company scope. Session POSTs require `X-CSRF-TOKEN`; bearer tokens require the `api` ability. JSON uses the existing `data` envelope and validation `errors` response.

Sales reuse the customer search, preview, seat reservation, SePay webhook and ticket issuer services. The snapshot stores the initiating operator separately; the passenger booking is a guest booking, never assigned to the employee. Keep the same UUID idempotency key and payload on uncertain retries. Pending intents are not successful sales: booking/tickets are returned only after an accepted webhook and matching completed payment. Sale reads are restricted to the initiating operator and current company. Demo routes are excluded. Directional search and pickup/drop-off use the existing customer services and validation. Each sale covers the selected outbound or return trip; it does not combine both legs into one payment. POST /api/v1/staff/ticket-quotes returns the canonical fare and boarding time without creating an intent. Promotions, exchange/cancellation and refunds are not added. Staff views live in Staff/TicketProcessing; Customer views remain unchanged.

Staff payment preview: POST /api/v1/staff/ticket-previews requires booking.create and the validated ticket-sale payload. Returns a read-only draft from PaymentPreviewBuilder when SePay is unavailable; does not reserve seats, create payment intents, or issue tickets. Staff round-trip sales forward both legs to the existing payment service and enforce the operator company scope for both trips.

Staff booking UI reuses Customer TripSearch and BookingManagement partials and FuteBus Payment styles. GET /api/v1/staff/ticket-trips returns the same result markup and company-scoped trip data. GET /api/v1/staff/ticket-trips/{trip}/booking returns the full customer booking markup, including both round-trip legs, stop selectors, vehicle popovers, terms and captcha. DELETE /api/v1/staff/ticket-sales/{sale} abandons only an unpaid payment preview; paid/review intents return 409. Session mutations require CSRF. Rendered payment/success/review markup is returned as data.html, with staff-owned navigation and customer ownership kept separate from the operator.

The staff sale now renders the complete customer hero, trip results, booking layout and partials, payment preview, review, and success receipt. Staff-owned entry fragments adapt only navigation, API submission and operator/customer identity. Shared Customer and Payment files are read-only. The previous simplified staff booking/payment partials were removed. The active sale id is retained in the staff URL for safe status restoration without creating another intent.

HTML form submissions to POST /api/v1/staff/ticket-sales now use the existing validated sale services and return HTTP 303 to /nhan-vien/thanh-toan/{sale}. When SePay is not ready, only a session-bound draft preview is rendered. JSON callers retain the existing 201/503 contract. Session form CSRF tokens are checked alongside the existing header token. The destination checks booking.create, operator/company ownership and preview expiry; real intent state is loaded from the service. Captcha completion uses the same native form.submit() operation as the customer booking UI.

Staff cash collection: `POST /api/v1/staff/ticket-sales/{sale}/cash` with `received: true` confirms the operator has physically collected the displayed amount. It requires `booking.create`, company/operator ownership, a server-side session draft and CSRF. Cash works without SePay configuration. Backend rechecks current fares, departure and both legs' seat availability under trip locks, then reuses `TicketIssuer` to issue guest customer tickets and inserts a completed `cash` payment with operator/company audit data in `payload`. The UUID-based payment code makes retries idempotent. No migration or shared Payment/Customer file change is needed. A pending SePay intent for this sale becomes expired; a later bank transfer goes through the existing reconciliation path rather than issuing duplicate tickets. Do not confirm cash when the customer has already transferred funds.

The payment countdown uses the server expiry and a monotonic local deadline, including time elapsed while a background tab throttles callbacks. The Back form uses Core's shared confirmation and DELETE API; acceptance abandons only an unpaid draft/intent and redirects with the original search criteria. It does not cancel issued tickets.
